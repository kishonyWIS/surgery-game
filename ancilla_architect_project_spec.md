# Ancilla Architect

## Project specification for an instance-specific qLDPC surgery puzzle and optimization tool

**Status:** Initial project plan  
**Primary reference:** [Parsimonious Quantum Low-Density Parity-Check Code Surgery](https://arxiv.org/pdf/2603.05082)  
**Primary objective:** Build a playable graph-complex editor in which a player constructs a small LDPC ancilla system for measuring a particular logical operator, while an automated validator finds unfilled cycles, overloaded checks, congestion, and expansion bottlenecks.

---

## 1. Executive summary

The paper proves that a weight-\(W\) logical Pauli operator in a general qLDPC code can be measured using an ancilla system with \(O(W\log W)\) qubits. This is a universal worst-case construction. For a specific code and a specific logical operator, a substantially smaller ancilla may exist.

Ancilla Architect turns the instance-specific optimization problem into a puzzle game:

1. Start from a measurement graph derived from a chosen logical operator.
2. Add auxiliary vertices, edges, and faces.
3. Ensure that every graph cycle is generated by face boundaries, so the ancilla has no internal logical operators.
4. Keep every vertex degree, face size, and edge-to-face incidence below fixed LDPC limits.
5. Ensure that the measurement graph has sufficient expansion, or eventually verify the distance of the merged code directly.
6. Minimize the number of edges, because edges of the ancilla complex correspond to physical ancilla qubits.

The first version should be both:

- a self-contained puzzle game for small graph instances; and
- a research tool that exports machine-verifiable candidate ancilla complexes.

The MVP should **not** attempt to implement the paper's full parsimonious-cone construction or exact merged-code distance. It should first establish a correct mathematical engine and usable graph editor.

---

## 2. Product vision

### 2.1 One-sentence pitch

> Build the smallest ancilla complex that measures the target logical before the noise adversary finds a homological hole, a low-expansion cut, or an overloaded check.

### 2.2 Player fantasy

The player is an architect designing a fault-tolerant measurement gadget. The graph is a physical network:

- vertices are measurement checks;
- edges are costly ancilla qubits;
- faces eliminate hidden logical operators;
- narrow cuts threaten distance;
- overloaded vertices and edges violate the LDPC constraints.

The player is not asked to reproduce a known construction. Any mathematically valid construction is accepted. The universal construction from the paper is a benchmark, not a prescribed solution.

### 2.3 Why this can be a research game

Every completed level is a certificate of an upper bound on the ancilla cost for a specific instance. A database of human-generated solutions could provide:

- warm starts for SAT, MILP, CP-SAT, MCTS, or local-search solvers;
- reusable graph gadgets;
- empirical evidence for when \(O(W)\) ancillas are possible;
- comparisons between instance-optimal constructions and the paper's \(O(W\log W)\) worst-case construction;
- training data for graph-based machine-learning agents.

## 3. Scope and staged development

### 3.1 MVP scope

The MVP receives a fixed measurement graph \(G\). The player may:

- add auxiliary vertices;
- add auxiliary edges;
- add faces specified by their boundary edges;
- remove player-added objects;
- move vertices for visualization;
- ask the adversary to find a failure witness;
- save and load a solution as JSON.

The MVP validates:

- preservation of the required measurement graph;
- connectivity;
- the chain condition \(\partial_1\partial_2=0\);
- \(H_1=0\);
- optionally \(H_2=0\);
- maximum vertex degree;
- maximum face weight;
- maximum edge-to-face congestion;
- Cheeger expansion of the measurement graph for small instances;
- the total ancilla-qubit count.

### 3.2 Explicitly out of scope for the MVP

Do not initially implement:

- import of arbitrary \(H_X\) and \(H_Z\) matrices;
- generation or optimization of the measurement-graph pairings;
- multiplication of the logical representative by stabilizers;
- the complete binary-tree shuffle and pruning construction from the paper;
- exact merged-code stabilizer construction;
- exact merged-code distance;
- circuit-level syndrome extraction or noise simulation;
- authentication, multiplayer, or a persistent online leaderboard;
- hardware geometry or routing.

These are later milestones. Keeping them out of the first version is important.

### 3.3 Recommended development order

1. Pure Python mathematical engine with tests.
2. JSON challenge and solution formats.
3. FastAPI validation service.
4. React graph editor.
5. Game feedback, attacks, scoring, and tutorial levels.
6. Measurement-graph construction from CSS code data.
7. Optimization and solver assistance.
8. Exact merged-code validation and research benchmarks.

## 4. Mathematical model

All linear algebra is over \(\mathbb F_2\).

### 4.1 Input from the data code

For an eventual full-code challenge, the input is a CSS code with parity-check matrices

\[
H_X^D,\qquad H_Z^D,
\]

and a chosen \(X\)-type logical representative

\[
\ell\in\ker H_Z^D
\]

that is not an \(X\)-stabilizer.

The logical support is

\[
V_\ell=\{q:\ell_q=1\},
\qquad
W=|V_\ell|.
\]

For each \(Z\)-check \(z\), the overlap

\[
\operatorname{supp}(z)\cap V_\ell
\]

has even cardinality. Pair the qubits in this overlap. Every pair becomes an edge of the measurement graph. Additional edges may be added, while keeping bounded degree, to make the graph connected and expanding.

The MVP skips this derivation and starts from the resulting graph.

### 4.2 Measurement graph

The measurement graph is

\[
G=(V_G,E_G).
\]

Its vertices correspond to data qubits in the logical support. Its required edges arise from paired \(Z\)-check overlaps. Optional measurement edges may be added to improve connectivity or expansion. In the eventual attachment map:

- a required edge maps to its associated data \(Z\)-check;
- an optional expansion edge maps to zero.

The data model must distinguish these two edge types.

### 4.3 Ancilla cell complex

The player constructs a length-two cell complex

\[
A_2\xrightarrow{\partial_2}A_1\xrightarrow{\partial_1}A_0.
\]

Interpretation:

| Mathematical object | Game object | CSS object |
| --- | --- | --- |
| Basis of \(A_0\) | Vertices | \(X\)-checks |
| Basis of \(A_1\) | Edges | Ancilla qubits |
| Basis of \(A_2\) | Faces | \(Z\)-checks |

The required measurement graph must occur as a literal subgraph of the one-skeleton \(A_1\to A_0\) in the MVP:

\[
G\subseteq A^{(1)}.
\]

Later versions may allow a bounded-congestion deformation of \(G\), as in the intermediate constructions of the paper.

### 4.4 Boundary maps

For an edge \(e=(u,v)\), define

\[
\partial_1 e=u+v.
\]

A face is stored as a set of edge IDs. Its boundary vector is

\[
\partial_2 f=\sum_{e\in\operatorname{boundary}(f)}e.
\]

Every face must satisfy

\[
\partial_1\partial_2f=0.
\]

This is the CSS commutation condition. Graphically, every vertex must meet an even number of edges in the boundary of a face.

For the MVP, require a face boundary to be one connected simple cycle, including a possible length-two cycle formed from parallel edges. Later, permit arbitrary cycle-space vectors, including disconnected unions of cycles.

### 4.5 Homology conditions

The first homology is

\[
H_1(A)=\ker\partial_1/\operatorname{im}\partial_2.
\]

The central validity requirement is

\[
H_1(A)=0.
\]

This means that every cycle of the one-skeleton is generated by face boundaries. Therefore, cycle-supported \(Z\)-operators are stabilizers rather than internal ancilla logical operators.

The relevant Betti numbers are

\[
\beta_0=|A_0|-\operatorname{rank}(\partial_1),
\]

\[
\beta_1=|A_1|-\operatorname{rank}(\partial_1)-\operatorname{rank}(\partial_2),
\]

and, because there is no \(A_3\),

\[
\beta_2=|A_2|-\operatorname{rank}(\partial_2).
\]

The paper's final cellulated cone satisfies

\[
\beta_0=1,\qquad \beta_1=0,\qquad \beta_2=0.
\]

For the first game mode:

- require \(\beta_0=1\);
- require \(\beta_1=0\);
- treat \(\beta_2=0\) as a standard validity condition so redundant faces cannot be added merely to manipulate presentation;
- later allow redundant faces in a separate mode where redundant syndrome information may be useful but carries an explicit cost.

### 4.6 LDPC constraints

Define:

\[
w_X(A)=\max_{v\in A_0}\deg(v),
\]

\[
w_Z(A)=\max_{f\in A_2}|\partial f|,
\]

and

\[
q_Z(A)=\max_{e\in A_1}|\{f:e\in\partial f\}|.
\]

Every graph edge has two endpoints, so its \(X\)-check incidence is automatically two in an ordinary graph complex.

A challenge specifies caps

\[
w_X(A)\le w_X^{\max},
\]

\[
w_Z(A)\le w_Z^{\max},
\]

and

\[
q_Z(A)\le q_Z^{\max}.
\]

The paper's universal construction gives constants depending only on the original graph degree \(\Delta\): face weight at most \(5\), edge-to-face incidence at most \(4+\Delta\), and vertex degree at most \(9+\Delta\). These are useful reference caps, not necessarily the best caps for a particular level.

### 4.7 Expansion and distance certificate

Let \(G_m\) denote the measurement graph after required and optional measurement edges have been chosen. Do **not** include purely auxiliary filling or routing edges when computing this expansion metric.

Use the unnormalized Cheeger constant

\[
h(G_m)=
\min_{\varnothing\ne S\subseteq V_G,\ |S|\le |V_G|/2}
\frac{|\partial S|}{|S|}.
\]

The paper proves for the correctly attached merged code \(M\) that

\[
d_X(M)\ge \min\{h(G_m),1\}d_X(D),
\]

while

\[
d_Z(M)\ge d_Z(D).
\]

In a theorem-certified game mode, require

\[
h(G_m)\ge h_{\min}.
\]

For example, \(h_{\min}=1\) yields the strongest bound provided by this expression. The paper also notes that the expander condition is often unnecessary in practice, so a later instance-specific mode should permit direct merged-distance verification instead.

### 4.8 Cost function

The primary physical cost is the number of ancilla qubits:

\[
Q_A=|A_1|.
\]

Use feasibility constraints rather than immediately mixing all metrics into one weighted objective. Among feasible solutions, compare the lexicographic tuple

\[
(|A_1|,|A_0\setminus V_G|,|A_2|,I),
\]

where

\[
I=\sum_{f\in A_2}|\partial f|
\]

is total face-edge incidence.

The leaderboard should order solutions by:

1. fewer ancilla qubits;
2. fewer auxiliary vertices;
3. fewer faces;
4. less total incidence;
5. larger expansion or exact merged distance as a tie-breaker.

## 5. Game design

### 5.1 Core loop

1. Inspect the required measurement graph.
2. Press **Attack** to reveal the most serious current defect.
3. Add or remove vertices, edges, or faces.
4. Watch the live homology and LDPC meters update.
5. Reach a valid construction.
6. Optimize it by removing unnecessary resources.
7. Submit it for an exact final validation.

### 5.2 Player actions

| Action | Mathematical effect | Typical benefit | Typical danger |
| --- | --- | --- | --- |
| Add auxiliary vertex | Add a basis element of \(A_0\) | Split a high-degree hub | Requires new edge-qubits |
| Add measurement edge | Add to \(G_m\) and \(A_1\) | Improve expansion | Costs a qubit and creates a new cycle if endpoints were connected |
| Add filling edge | Add only to \(A_1\) | Split long cycles or route locally | Costs a qubit and may create extra cycles |
| Add face | Add a column of \(\partial_2\) | Kill a homology class | Raises face weight and edge congestion |
| Remove player object | Delete an auxiliary cell | Reduce cost | May reintroduce a hole or bottleneck |
| Contract path | Replace a degree-two chain | Reduce qubits | Can make adjacent faces nonlocal |
| Duplicate/reroute path | Spread incidence | Reduce congestion | Adds qubits |

Required graph vertices and required measurement edges are immutable. Optional measurement edges and all auxiliary cells are editable.

### 5.3 Automated adversary

The adversary does not simulate random noise in the MVP. It produces deterministic mathematical witnesses.

#### Ghost-logical attack

If \(\beta_1>0\), return an edge vector

\[
c\in\ker\partial_1\setminus\operatorname{im}\partial_2.
\]

Highlight the corresponding cycle or cycle union in red.

#### Bottleneck attack

Return a subset \(S\subseteq V_G\) minimizing the Cheeger ratio, and highlight:

- vertices in \(S\);
- vertices outside \(S\);
- crossing measurement edges.

#### Overload attack

Return the most severe violation among:

- vertex degree;
- face boundary size;
- edge-to-face congestion.

#### Redundancy attack

If \(\beta_2>0\), return a set of faces whose boundaries sum to zero.

#### Distance attack

This is a post-MVP feature. It should return a low-weight logical operator of the merged code whenever the requested distance is not achieved.

### 5.4 Feedback meters

The main screen should always display:

- ancilla qubits: \(|A_1|\);
- auxiliary vertices;
- number of faces;
- connected components: \(\beta_0\);
- unresolved holes: \(\beta_1\);
- redundant face relations: \(\beta_2\);
- maximum vertex degree;
- maximum face size;
- maximum face congestion per edge;
- Cheeger constant or current best bottleneck;
- solution validity;
- score relative to the level baseline.

### 5.5 Stars and progression

- **One star:** Produce any valid complex.
- **Two stars:** Beat the ordinary-cone baseline.
- **Three stars:** Beat the best built-in heuristic.
- **Platinum:** Match a solver-certified optimum.

Avoid comparing against the asymptotic \(O(W\log W)\) expression directly. Compare finite constructions on the exact same instance.

### 5.6 Game modes

#### Campaign

Handcrafted teaching levels with a restricted action set.

#### Sandbox

Load or draw a graph and design any filling.

#### Research challenge

Load an instance generated from a real CSS code and logical operator. Export a formal certificate.

#### Daily challenge

All players receive the same graph and caps. This requires persistence and a server, so it is not part of the MVP.

#### Architect versus Saboteur

A future two-player mode. The architect edits the complex; the saboteur selects a cycle, cut, or hotspot. A claimed attack scores only if the validator confirms it.

## 6. Tutorial level sequence

### Level 1: One square, one hole

Input: a four-cycle.  
Caps: face weight \(4\).  
Lesson: add one square face and make \(\beta_1\) go from \(1\) to \(0\).

### Level 2: Triangles only

Input: the same four-cycle.  
Caps: face weight \(3\).  
Lesson: add one diagonal edge and two triangular faces.

Expected result:

- \(5\) edge-qubits;
- \(2\) faces;
- \(\beta_1=\beta_2=0\).

### Level 3: The cone trap

Input: an eight-cycle.  
Caps: face weight \(3\), vertex degree \(4\).  
Lesson: an ordinary apex cone violates the degree cap. Find a bounded-degree triangulation or splitter construction.

### Level 4: Shared edges

Input: a theta graph with cycle rank \(2\).  
Lesson: independently chosen faces may overload a shared edge. Choose a better cycle basis.

### Level 5: Expansion

Input: two dense subgraphs connected by a narrow bridge.  
Lesson: \(H_1=0\) is not enough. Add optional measurement edges to repair the bottleneck while respecting degree caps.

### Level 6: Prune

Input: a valid but deliberately bloated complex.  
Lesson: remove unused branches and contract safe nonbranching paths without changing homology.

### Level 7: Pairing choices

Post-MVP. Give the support of a logical and several even check overlaps. Let the player choose pairings before filling the graph.

### Level 8: Real qLDPC instance

Post-MVP. Import a small CSS code and compare the player's result with a baseline generated from the paper.

## 7. Technical architecture

### 7.1 Recommended stack

Use a small monorepo:

- **Frontend:** React and TypeScript created with Vite.
- **Graph canvas:** Cytoscape.js.
- **Backend:** Python with FastAPI.
- **Mathematics:** custom bitset-based \(\mathbb F_2\) linear algebra plus NetworkX for ordinary graph algorithms where useful.
- **Optimization later:** Google OR-Tools CP-SAT.
- **Tests:** pytest for the backend; Vitest and React Testing Library for the frontend; Playwright later for end-to-end tests.

Reasons:

- Cytoscape.js is designed for interactive graph visualization and supports serialization, event handling, layouts, parallel edges, and headless graph analysis: <https://js.cytoscape.org/>.
- FastAPI provides a lightweight typed Python API and keeps future QEC and optimization code in Python: <https://fastapi.tiangolo.com/>.
- Vite provides a minimal React/TypeScript development setup: <https://vite.dev/guide/>.
- CP-SAT supports Boolean/XOR-style constraint modeling and can later solve expansion and completion subproblems: <https://developers.google.com/optimization/cp/cp_solver>.

Do not pin versions in this design document. Pin them in the lockfiles when the repository is initialized.

### 7.2 Why use a Python backend

The graph editor alone could run entirely in the browser, but the project is intended to become a research tool. Python is the better home for:

- binary linear algebra;
- code-distance routines;
- QEC matrix import;
- NetworkX graph algorithms;
- MILP/CP-SAT solvers;
- integration with existing code and Stim-related research tooling.

The backend should be the source of truth for final validation. The frontend may compute approximate live metrics for responsiveness, but a submitted solution is valid only if the backend accepts it.

## 9. Core algorithms

### 9.1 Binary-vector representation

For small and medium graphs, represent a vector over \(\mathbb F_2\) as a Python integer:

- bit \(i\) is the coefficient of basis element \(i\);
- addition is XOR;
- membership and pivot operations are bit operations.

This is simpler and often faster than using dense NumPy arrays for the initial scale of the game.

Maintain deterministic maps:

```python
vertex_index: dict[str, int]
edge_index: dict[str, int]
face_index: dict[str, int]
```

### 9.2 Rank over \(\mathbb F_2\)

Implement:

```python
def gf2_rank(columns: list[int]) -> int: ...
def gf2_basis(vectors: list[int]) -> dict[int, int]: ...
def gf2_reduce(vector: int, basis: dict[int, int]) -> int: ...
def gf2_in_span(vector: int, basis: dict[int, int]) -> bool: ...
```

Use the most significant set bit or least significant set bit as a deterministic pivot. Add unit tests before writing any API or UI.

### 9.3 Construct \(\partial_1\)

For every edge \(e=(u,v)\), create the vertex-space bitset

\[
b_e=2^{i(u)}\oplus 2^{i(v)}.
\]

The list of these columns represents \(\partial_1\).

### 9.4 Construct \(\partial_2\)

For every face, create an edge-space bitset whose selected bits are `boundaryEdgeIds`. These are the columns of \(\partial_2\).

Validate every face by XORing the \(\partial_1\) columns of its boundary edges. The result must be zero.

### 9.5 Compute homology

Compute:

```python
rank_d1 = gf2_rank(boundary1_columns)
rank_d2 = gf2_rank(boundary2_columns)

beta0 = n_vertices - rank_d1
beta1 = n_edges - rank_d1 - rank_d2
beta2 = n_faces - rank_d2
```

Only use the \(\beta_1\) expression after verifying \(\partial_1\partial_2=0\).

Also verify the Euler-characteristic identity:

\[
\beta_0-\beta_1+\beta_2=|A_0|-|A_1|+|A_2|.
\]

Use this as an internal consistency assertion in tests.

### 9.6 Find a ghost-cycle witness

1. Build a spanning forest of the one-skeleton.
2. For every non-tree edge, construct its fundamental cycle.
3. Row-reduce the selected face boundaries to obtain a basis of \(\operatorname{im}\partial_2\).
4. Reduce each fundamental cycle modulo the face-boundary basis.
5. Return the first cycle with nonzero remainder.

If every fundamental cycle is in the face span, then \(H_1=0\).

For better game feedback, try to return a short witness:

- sort fundamental cycles by length;
- test short cycles first;
- later solve for a minimum-weight nontrivial homology representative.

### 9.7 Find a redundant-face witness

Track dependencies during Gaussian elimination of the \(\partial_2\) columns. If a face column reduces to zero, return the corresponding XOR combination of face IDs. That combination is a nonzero element of \(\ker\partial_2\).

### 9.8 Degree and congestion

Compute:

```python
vertex_degree[v] = number of incident edges
face_weight[f] = number of boundary edges
edge_face_congestion[e] = number of selected faces containing e
```

Parallel edges are distinct edge IDs and must be counted separately.

### 9.9 Connectivity

Use a disjoint-set union structure or BFS. Homological \(\beta_0\) should agree with the number of graph components. Assert this agreement in tests.

### 9.10 Exact Cheeger constant for small graphs

For \(|V_G|\le 24\), enumerate all nonempty subsets up to half the vertices. Use complement symmetry and fix one chosen vertex outside \(S\) to halve the search space again.

Return both:

- the exact value \(h(G_m)\);
- the minimizing subset \(S\).

This is exponential and should run only on explicit request or after a debounce, not on every mouse movement.

### 9.11 CP-SAT Cheeger computation for larger graphs

Post-MVP, compute the exact Cheeger constant by solving one cut problem for each cardinality \(k\):

- Boolean variable \(s_v\) indicates whether \(v\in S\);
- impose \(\sum_v s_v=k\);
- Boolean variable \(x_e=s_u\oplus s_v\) indicates whether edge \(e=(u,v)\) crosses the cut;
- minimize \(\sum_e x_e\).

Then

\[
h(G_m)=
\min_{1\le k\le |V_G|/2}
\frac{\operatorname{mincut}(k)}{k}.
\]

This is an appropriate use of CP-SAT because the edge-crossing relation is Boolean XOR. Cache results using a canonical hash of the measurement graph.

### 9.12 Incremental validation

Correctness comes before incremental performance. Initially recompute all metrics after each committed move.

After profiling, optimize:

- degree updates locally;
- face congestion locally;
- maintain a dynamic XOR basis for face boundaries;
- cache \(\partial_1\) while only faces change;
- recompute expansion only when measurement edges change;
- debounce backend validation by approximately 150–300 ms.

### 9.13 Exact merged-code distance

Post-MVP:

1. Construct the full attachment chain map.
2. Generate the merged CSS matrices \(H_X^M,H_Z^M\).
3. Verify commutation and the expected number of logical qubits.
4. Solve minimum-weight logical problems:

\[
d_X(M)=
\min_{x\in\ker H_Z^M\setminus\operatorname{row}(H_X^M)}|x|,
\]

\[
d_Z(M)=
\min_{z\in\ker H_X^M\setminus\operatorname{row}(H_Z^M)}|z|.
\]

Do not mix this into the initial homology engine. Keep it as a separate validator.

## 10. Validation pipeline

Run validation in this order so error messages are meaningful:

1. Validate JSON schema.
2. Check unique stable IDs.
3. Check that all edge endpoints exist.
4. Check that all face-edge references exist.
5. Check that immutable challenge cells remain present and unchanged.
6. Check for disallowed self-loops.
7. Build the boundary maps.
8. Check \(\partial_1\partial_2=0\) face by face.
9. Check connectedness and \(\beta_0\).
10. Compute \(\beta_1\) and a witness if nonzero.
11. Compute \(\beta_2\) and a witness if nonzero.
12. Compute vertex degrees, face weights, and edge congestion.
13. Compute expansion only if requested by the challenge.
14. Compute the lexicographic score.
15. Return all defects, not only the first one.

Every validation issue should contain:

- a stable code such as `NONTRIVIAL_H1`;
- human-readable text;
- severity;
- implicated vertex, edge, and face IDs;
- a suggested repair category, not a prescriptive exact move.

Example:

```json
{
  "code": "NONTRIVIAL_H1",
  "severity": "error",
  "message": "The complex contains an unfilled cycle.",
  "edgeIds": ["e0", "e1", "e2", "e3"],
  "suggestion": "Add a face whose boundary spans this cycle, or add edges that split it into fillable cycles."
}
```

## 13. Built-in baselines and hints

### 13.1 Direct-face baseline

Compute a fundamental cycle basis. If every cycle length is below the face cap and congestion is legal, add one face per basis cycle.

### 13.2 Ordinary-cone baseline

Add one apex connected to every measurement vertex and one triangular face per measurement edge. This is a useful teaching baseline but may violate the degree cap.

### 13.3 Shortest-cycle-basis heuristic

Compute a minimum-weight cycle basis and add allowed faces for its cycles. If a cycle is too long, leave it unresolved and report it.

### 13.4 Chord-splitting heuristic

For a long basis cycle:

1. choose two well-separated vertices;
2. add a chord;
3. replace the long cycle by the two resulting cycles;
4. reject the chord if it violates the degree cap;
5. iterate until all cycles meet the face cap.

Because every added chord raises the cycle-space dimension by one, include both child cycles in the updated basis rather than pretending the chord simply deletes homology.

### 13.5 Congestion-aware heuristic

Assign each potential face a cost

\[
c(f)=\alpha|\partial f|
+\beta\sum_{e\in\partial f}\operatorname{congestion}(e)
+\gamma\max_{v\in\partial f}\deg(v).
\]

Use this only as a heuristic for hints. It is not the final game score.

### 13.6 Parsimonious-cone baseline

Implement this only after the editor and validator are mature. It requires:

- bipartite subdivision;
- endpoint-pair labels;
- a sequence of noninteracting adjacent bit swaps;
- interpolating tree complexes;
- pruning to actual edge labels;
- contraction of nonbranching chains;
- cellulation to recover the original graph as a literal subgraph.

Treat this as an independent algorithm module with its own extensive tests.

## 14. Solver roadmap

### 14.1 Fixed graph, select faces

Given a fixed one-skeleton and a candidate list of short cycles, choose a set of face boundaries that spans the cycle space while respecting edge congestion.

Variables:

\[
y_f\in\{0,1\}.
\]

Constraints:

- selected face boundaries span \(\ker\partial_1\);
- edge congestion is bounded;
- selected faces are independent if \(H_2=0\) is required.

The spanning/rank constraint is the difficult part. Start with lazy cuts:

1. solve a relaxed face-selection problem;
2. compute an unfilled cycle;
3. add a constraint requiring future selected faces to span that witness;
4. repeat.

### 14.2 Fixed vertex set, add edges and faces

Provide a finite candidate universe of additional edges and short cycles. Select both:

\[
x_e,y_f\in\{0,1\}.
\]

Impose:

\[
y_f\le x_e
\]

for every \(e\in\partial f\), together with degree and congestion caps.

### 14.3 Add Steiner vertices

Provide a bounded number of auxiliary vertex slots and candidate incidence patterns. Symmetry breaking is essential because auxiliary vertices are otherwise interchangeable.

Possible symmetry-breaking rules:

- activate auxiliary vertices in ID order;
- lexicographically order their neighborhoods;
- disallow isolated active vertices;
- require every active filling edge to participate in a path or face.

### 14.4 Local-search solver

Before a full exact solver, implement stochastic local search with moves identical to game actions:

- add/remove chord;
- add/remove face;
- split overloaded vertex;
- contract degree-two vertex;
- reroute a face boundary;
- change a measurement pairing later.

Use a penalty objective:

\[
E=
M Q_A
+P_{H_1}\beta_1
+P_{\mathrm{conn}}(\beta_0-1)
+P_X\operatorname{overload}_X
+P_Z\operatorname{overload}_Z
+P_q\operatorname{congestionOverload}
+P_h\operatorname{expansionDeficit},
\]

with feasibility penalties much larger than the qubit cost. Human solutions can seed this search.

### 14.5 Joint measurement-graph optimization

Post-MVP, include variables for:

- the representative \(\ell\) within its stabilizer equivalence class;
- pairings of every even \(Z\)-check overlap;
- optional expansion edges;
- the filling complex.

This is likely the scientifically most interesting version, but it should be built only after the fixed-graph problem is reliable.

## 15. Testing strategy

### 15.1 Unit-test fixtures

Implement at least these exact fixtures:

1. **One isolated vertex:** \(\beta_0=1,\beta_1=0\).
2. **Two disconnected edges:** \(\beta_0=2\).
3. **Tree on five vertices:** \(\beta_1=0\) without faces.
4. **Four-cycle without a face:** \(\beta_1=1\).
5. **Four-cycle with one square face:** \(\beta_1=0,\beta_2=0\).
6. **Four-cycle with a diagonal and two triangles:** \(\beta_1=0,\beta_2=0\).
7. **Duplicate square face:** \(\beta_2=1\).
8. **Theta graph:** cycle rank \(2\).
9. **Two parallel edges:** cycle rank \(1\); optionally allow a weight-two face.
10. **Ordinary cone over a cycle:** \(H_1=0\), apex degree equal to the cycle length.

### 15.2 Property tests

For randomly generated small complexes:

- compare `gf2_rank` with a slow reference implementation;
- verify \(\partial_1\partial_2=0\) for generated face cycles;
- verify Euler characteristic;
- verify \(\beta_0\) agrees with connected components;
- verify every returned ghost witness is a cycle and not in the face span;
- verify every returned redundant-face witness sums to zero;
- verify serialization round trips preserve the validation report;
- verify reordering arrays does not change mathematical results or solution hash.

Use a property-based testing library such as Hypothesis on the Python side.

### 15.3 API tests

- malformed IDs are rejected;
- missing edge endpoints are rejected;
- faces referencing unknown edges are rejected;
- mutation of immutable cells is rejected;
- valid tutorial solutions are accepted;
- invalid tutorial solutions return the expected attack witness.

### 15.4 Frontend tests

- selecting boundary edges creates the intended face payload;
- deleting a vertex also requests deletion or handling of incident editable edges;
- immutable objects cannot be deleted;
- undo and redo are exact;
- attack witnesses highlight the correct cells;
- imported JSON is not trusted until backend validation succeeds.

## 19. Design decisions that should not be deferred

### 19.1 Faces are abstract

A face is defined by edge incidence, not by the current two-dimensional drawing. The graph may be nonplanar, and moving nodes must never change the complex.

### 19.2 Multigraphs are supported

Different data checks can produce the same paired endpoints. Edge IDs, not endpoint pairs, identify qubits.

### 19.3 The backend is authoritative

The frontend may preview metrics, but only backend validation determines validity and score.

### 19.4 Expansion uses only measurement edges

Filling edges must not silently improve the distance certificate. Tag edge roles and compute the Cheeger constant only on the measurement graph.

### 19.5 Fixed caps define a challenge

Do not reward an invalid low-qubit construction through a soft score. A construction either satisfies the specified LDPC and expansion caps or it does not.

### 19.6 Preserve exact witnesses

Every failed property should produce a concrete certificate that can be highlighted and independently tested.

### 19.7 Separate graph validity from surgery validity

The MVP verifies a valid ancilla complex for a fixed measurement graph. It does not yet prove that an arbitrary imported object implements the intended logical measurement. That claim should appear only after the attachment map and merged code are implemented.

## 20. Risks and mitigations

### Risk: The UI implies planar topology

**Mitigation:** Store faces as edge vectors; use highlighting instead of relying on filled geometric polygons.

### Risk: Exact expansion freezes interaction

**Mitigation:** Run it on demand, cache it, use a worker or backend job, and impose a small-instance limit. Display a discovered cut as an upper bound when using heuristics.

### Risk: Solver scope consumes the project

**Mitigation:** Complete the validator and manual game first. A human-playable editor is already useful without an exact optimizer.

### Risk: Homology code silently returns wrong answers

**Mitigation:** Use bitset and slow reference implementations in tests, Euler-characteristic checks, property testing, and explicit witnesses.

### Risk: Adding faces is too easy

**Mitigation:** Tight face-weight and congestion caps create the puzzle. Some levels should also restrict allowed actions.

### Risk: Game score diverges from physical usefulness

**Mitigation:** Keep a Pareto-style metrics panel, export all raw metrics, and later include exact merged distance and syndrome-extraction cost.

### Risk: The paper baseline is difficult to implement

**Mitigation:** Begin with direct-face, ordinary-cone, minimum-cycle-basis, and chord-splitting baselines. Add the exact parsimonious construction only as a later independent module.

## 21. Post-MVP research directions

### 21.1 Optimize the logical representative

Allow the player or solver to replace

\[
\ell\mapsto \ell+s,
\]

where \(s\) is an \(X\)-stabilizer. A minimum-weight representative need not minimize the final ancilla cost.

### 21.2 Optimize overlap pairings

Treat the perfect matching inside every even \(Z\)-check overlap as a game decision or solver variable.

### 21.3 Minimum local cycle-basis completion

Given \(G\), find the smallest bounded-degree augmentation \(H\supseteq G\) whose cycle space has a basis \(\mathcal B\) satisfying

\[
\max_{\gamma\in\mathcal B}|\gamma|\le w_Z^{\max}
\]

and

\[
\max_e|\{\gamma\in\mathcal B:e\in\gamma\}|\le q_Z^{\max}.
\]

This formalizes the chord-adding and separate-face strategy discussed during the paper analysis.

### 21.4 Learn reusable gadgets

Mine submitted solutions for recurring replacements of:

- high-degree cone apices;
- long cycles;
- congested shared paths;
- low-expansion cuts.

Store gadgets with typed boundary interfaces so they can be reused by solvers.

### 21.5 Parallel logical measurements

Allow several commuting logical operators to share parts of their ancilla systems. Optimize total qubits and spacetime volume rather than constructing one cone per logical.

### 21.6 Hardware-aware mode

Add a hardware graph and require every ancilla interaction to be embeddable. Include SWAP or routing cost in the score.

### 21.7 Circuit-level mode

Compile the final checks into syndrome-extraction circuits and score:

- number of ancilla qubits;
- circuit depth;
- maximum check schedule conflict;
- hook-error behavior;
- circuit-level distance;
- total occupied spacetime volume.

### 21.8 Automated agents

Expose game moves through an API for:

- MCTS;
- reinforcement learning;
- graph neural policies;
- evolutionary search;
- LLM-based agents using verifier feedback.

The deterministic adversary witnesses make this unusually well suited to verifier-guided agents.
